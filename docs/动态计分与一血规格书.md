## 1. 背景与目标

社团以往线下赛使用纸质计分，线上迁移后采用「每题固定 1 分」是为了降低实现成本。随着题量增加与正式赛制对齐需求增强，需要：

1. 题目可配置不同基础分，体现难度差异；
2. 记录并展示一血（First Blood），用于赛后讲评与激励；
3. 为后续衰减、奖金、冻结、治理概览预留同一套数据模型（P0 只落地最小闭环，但命名与分层必须能承接 P1/P2）。

非目标（明确不做）：工单客服、私信、积分商城兑换、投票问卷、本地桌面工具、任何娱乐向小游戏玩法。本模块仅服务 Flag 校验后的计分与一血。

## 2. 术语

- **基础分**：题目被正确解出时可获得的基准分值来源；语义对齐现有 `questions.points`，允许扩展字段名，但禁止继续写死常量 `1`。
- **一血**：某题在全场范围内第一次被判定为正确提交的事件；一题至多一条。
- **解出次数**：某题累计被正确解出的人次（含一血那一次）。错误提交不计入。
- **入账分**：写入该参赛者总分时实际加上的分值；P0 等于基础分；P1 起可能变为「解出当时的当前分 + 可能的一血奖金」。
- **配置键命名空间**：凡本模块写入 `contest_config`（或等价配置）的键，必须使用前缀 `scoring.`（注意带点号），不得使用无前缀短名，以免与历史 `readyTime`/`startTime` 等键冲突。

## 3. 范围与分期

| 分期 | 对应出题轮次 | 必须交付 | 明确不做 |
|------|--------------|----------|----------|
| P0 | 第 1 轮 | 一血落库、基础分入账、榜单反映、管理端一血只读、独立模块分层 | 衰减、奖金、概览统计、冻结 |
| P1 | 第 2 轮 | 衰减、解出当时分入账、一血奖金、配置读写 | 新建第二套计分表/Service |
| P2 | 第 3 轮 | 计分概览、赛期门禁与赛后冻结、三轮约定回溯 | 新建冗余统计表 |

## 4. 工程约束（全局，三轮均有效）

**条款 A1（依赖）**：前端不得为完成本模块新增任何 npm 依赖；继续使用现有 axios 封装与 Tailwind。后端不得引入 Redis、消息队列或第二套 ORM；持久化继续 MyBatis，且 mapper 必须使用 XML（与 announcement、hint 等现有写法一致），禁止改成纯注解 SQL 来「图省事」。

**条款 A2（分层）**：必须新增独立的计分/一血 Service（类名自定），禁止把核心业务堆进现有 `ContestService` / `AdminService`。Controller 只做鉴权与参数转发。Mapper / Entity / XML 与 Service 一一对应，不得在 Controller 里直接注入 Mapper 写业务。

**条款 A3（风格）**：数据库字段 snake_case；Java 与前端 JS/Vue 使用 camelCase；所有新接口响应继续包装为项目既有 `ApiResponse`；鉴权继续 JWT，管理端接口沿用现有 admin 权限检查方式。

**条款 A4（命名冻结）**：第 1 轮自行决定的一血表名、基础分字段名、计分 Service 类名、本模块 API 路径前缀，自第一次提交约定清单起视为冻结；第 2、3 轮只允许扩展，不允许改名或再造同义结构。

## 5. P0 数据模型要求

一血持久化至少能还原：`question_id`、达成一血的 `user_id`（或与现有用户体系一致的关联键）、达成时间。同一 `question_id` 必须有数据库层唯一约束（不能只靠应用层 if）。建议同时记录可选的 `contest_user_id` 以便与 `contest_users` / `submissions` 对齐，但是否冗余由实现者权衡，权衡结论写进约定清单。

题目基础分：以现有 `questions.points` 为语义来源。若选择重命名列、增加镜像列或在代码层把 `points` 当作基础分读取，必须在约定清单里写清「最终选用的字段名」——后轮说的「基础分字段」均指该名字。

错误提交、重复提交已解出题、提示解锁扣分：P0 不改变 `HintService` 既有扣分逻辑；但入库一血与基础分入账必须发生在「本次提交被判定正确」的同一事务路径上，避免出现「榜上加了分但一血表无行」或相反的撕裂。

## 6. P0 接口与界面

参赛者侧：榜单与个人得分必须反映新的入账分；无需单独做「我的一血」页，但不得因改造导致原答题/提交流程不可用。

管理端：提供每题一血只读信息（用户标识 + 达成时间）。可以挂在 Admin 现有页面新区，或独立子区；前端改动仍走现有路由与组件风格。

安全：一血写入只允许由服务端在正确提交时触发，禁止提供「手动指定某人获得一血」的公开接口（管理端只读）。

## 7. 与现有提交表的关系（易漏）

现有 `submissions` 表以 `(contest_user_id, question_id)` 唯一，表示每题至多一条提交记录语义。一血表描述的是「全场第一」，粒度是题目全局，不是 per-user。实现时不得用「某用户 submissions 是否正确」误判为一血；必须在全场维度判断「该题此前是否已有正确解出」。

## 8. 配置键预留清单（P0 可不写入默认值，但键名已冻结）

以下键名在 P1/P2 启用，**键字符串必须与下表完全一致**（含 `scoring.` 前缀）。P0 若提前插入默认值亦可，但不得改名：

| 配置键 | 类型语义 | 默认值 | 启用分期 |
|--------|----------|--------|----------|
| `scoring.min_points` | 非负整数 | `1` | P1 |
| `scoring.decay_step` | 非负整数 | `0` | P1 |
| `scoring.first_blood_bonus` | 非负整数 | `0` | P1 |
| `scoring.freeze_on_end` | 布尔（建议存 `true`/`false` 字符串） | `true` | P2 |
| `scoring.overview_timezone` | 字符串 | `Asia/Shanghai` | P2（概览「近 24 小时」边界用，即使 P2 不做近 24h 指标也不得删除该键约定） |

注意：历史配置键 `startTime`、`endTime`、`readyTime`、`resultsTime` 仍由 `ContestTimeUtil` / `ConfigService` 管理，本模块赛期判断必须复用它们，禁止平行维护第二套比赛时间。

## 9. P1 衰减与入账（P0 不实现；第 2 轮按条款号验收）

**条款 B1**：题目当前分计算公式为

`current_points = max(scoring.min_points, 基础分 - scoring.decay_step × solve_count)`

其中 `solve_count` 为该题已被正确解出的次数；**计算当前分时，对「即将入账的这一次解出」：先用「入账前」的 `solve_count` 代入公式得到该次入账分，再增加解出次数**——即第 N 次解出使用的是衰减序列中第 N 档之前的值（N 从 1 开始时，第一次解出应仍接近基础分，具体以「入账前 solve_count」为准）。

**条款 B2**：已入账分数永不因后续衰减被改写；衰减只影响尚未解出的参赛者。

**条款 B3**：`scoring.first_blood_bonus` 仅在写入一血成功的那一次一并加到该用户总分；必须依赖一血表的唯一约束保证不重复发放；禁止另建「奖金发放表」做去重。

**条款 B4**：`scoring.decay_step = 0` 时行为应退化为「恒等于基础分（再夹逼到 min_points）」；自动化或手动测试需覆盖该分支。

**条款 B5**：提示解锁产生的扣分与动态分值正交：先按本题入账分加分，再按既有 hint 逻辑扣罚（若有），不得把 hint 扣分折算进 `decay_step`。

## 10. P1 接口挂载约定

衰减相关配置的读、写接口必须挂在 P0 已建立的「计分模块 API 路径前缀」之下，保持同一 Controller 或同一前缀风格，不得散落到无关联的 `/config` 旧接口里「顺便改一下」却不在约定清单中声明——若复用旧配置接口，也必须在第 2 轮说明里写明「复用了第一轮前缀下的哪条路径 / 或显式声明复用 `/api/...` 哪条已有配置接口」。

## 11. P2 冻结与门禁（P0 不实现；第 3 轮按条款号验收）

**条款 C1**：当比赛状态为「未开始」（现有时段工具中 start 之前）时，禁止产生一血行，禁止因正确提交增加总分中的动态分值部分。

**条款 C2**：当比赛状态为「已结束」且 `scoring.freeze_on_end` 为 true 时，冻结计分：不再接受新的正确计入与一血；只读查询（榜单、一血、概览）仍可用。若 `scoring.freeze_on_end` 为 false，则结束仍可入账（用于加时赛演练），但默认必须为 true。

**条款 C3**：公布成绩阶段（results 之后）的只读行为与现网一致，不得因本模块导致排行榜路由失效。

## 12. P2 计分概览指标定义（第 3 轮实现；指标口径不得自行发挥）

管理端概览必须提供且仅需提供以下聚合（名称可中文化，口径必须一致）：

1. `total_correct_solves`：全场正确解出总次数（按解出事件计，不是按题目数）；
2. `questions_with_first_blood`：已产生一血的题目数；
3. `questions_at_base_points`：按当前衰减公式计算后，当前分仍等于该题基础分的题目数；
4. `questions_at_min_points`：当前分已等于 `scoring.min_points` 的题目数；
5. `total_first_blood_bonus_awarded`：已发放的一血奖金合计（分值求和）。

**条款 D1**：以上聚合必须基于 P0/P1 的一血表与计分逻辑现场计算，禁止新建 `scoring_stats` 之类冗余汇总表。

**条款 D2**：概览接口属于管理端，权限模型与现有 `/admin/**` 一致。

## 15. 附录：示例推演（帮助理解 B1，数值仅示例）

设某题基础分 = 100，`scoring.decay_step = 10`，`scoring.min_points = 60`，`scoring.first_blood_bonus = 15`。

- 第 1 次正确解出前 solve_count=0 → 入账分 = max(60, 100-10×0)=100，若同时拿一血再 +15，用户该题贡献 115；此后一血表已有行。
- 第 2 次解出前 solve_count=1 → 入账分 = max(60, 100-10×1)=90，无一血奖金。
- 持续解出直到公式结果 ≤60 后，入账分钳制为 60。

若有人在衰减后要求「把第一名的 115 改成按最新当前分重算」，必须拒绝——违反 B2。
