## ② 一血表名及字段

表名：`first_bloods`

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | INT PK AUTO_INCREMENT | 一血记录ID |
| `question_id` | INT NOT NULL | 题目ID，**`UNIQUE KEY unique_first_blood_question (question_id)`** 库级唯一约束（§5），FK → `questions(id)` |
| `user_id` | INT NOT NULL | 达成一血的用户ID，FK → `users(id)` |
| `contest_user_id` | INT NOT NULL | 比赛用户ID（冗余），FK → `contest_users(id)` |
| `achieved_at` | TIMESTAMP DEFAULT CURRENT_TIMESTAMP | 达成时间 |

**冗余权衡结论（§5 要求写明）**：选择冗余 `contest_user_id`。理由：与 `submissions`/`contest_users` 对齐后，P2 概览聚合（§12）与后续审计可免二次回查 `contest_users`；代价仅每题一行的单字段冗余，可接受。

**一血判定方式（§7）**：不以 per-user `submissions` 判断；正确入账时执行 `INSERT IGNORE INTO first_bloods ...`，受影响行数 = 1 即全场首个（唯一约束保证并发下同题至多一条，应用层无 if 判断）。

## ③ 基础分最终字段名

**`questions.points`**（Java：`Question.points`，沿用现有列，不改名、不加镜像列）。
语义即规格书 §2「基础分」；P0 入账分 = 该字段值；代码中无任何写死 `+1`。后轮条款所称「基础分字段」均指此名。

## ④ 计分 Service 类名

**`com.ctf.service.ScoringService`**

- P0 方法：`recordCorrectSolve(ContestUser, Question): int`（同事务内一血落库 + 累加入账分，§5 同事务路径）、`getFirstBloodList(): List<FirstBloodItem>`（管理端只读）。
- P1 衰减/奖金、P2 冻结/概览均在本类扩展，不新建第二套 Service（§3、§13）。

## ⑤ 本模块 API 路径与方法

路径前缀：**`/api/scoring`**（冻结；P1 衰减配置读写、P2 概览均挂此前缀下，§10）。

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/scoring/first-bloods` | 管理端只读：全场各题一血（题目 + 学号/姓名 + 达成时间）；admin 角色校验方式与 `AdminController` 一致；响应包装 `ApiResponse`（A3） |

无任何写接口：一血写入仅由服务端在正确提交事务内触发（§6 安全）。前端对应 `scoringAPI.getFirstBloods()`。

## ⑥ §8 `scoring.*` 配置键预置情况

**未预置任何默认值**（§8 允许 P0 不写入）。键名已冻结，后轮启用时键字符串必须与规格书 §8 完全一致（`scoring.min_points`、`scoring.decay_step`、`scoring.first_blood_bonus`、`scoring.freeze_on_end`、`scoring.overview_timezone`），不改名。赛期时间判断继续复用 `ContestTimeUtil`（`contest.startTime` 等历史键），未平行维护第二套比赛时间。

## 计分模块备忘

- **B1 时点选择（预答 Z9）**：solve_count 取**入账前**。实现上 `recordCorrectSolve` 在本次提交写入 `submissions` 之前被调用，`countCorrectByQuestionId` 统计的是不含本次的全场正确解出次数；第 1 次解出代入 0（入账=基础分），第 N 次代入 N-1，与 §15 示例一致。
- **B2**：已入账分只进 `contest_users.total_score` 累加，无任何回算路径。
- **B3**：奖金发放与 `first_bloods` 的 `unique_first_blood_question` 唯一约束绑定——`INSERT IGNORE` 受影响行数=1 才加奖金，并发下同题至多一人得奖，无奖金发放表。
- **B4**：`decay_step=0` 时 `max(min_points, base-0)` 恒等于基础分（夹逼），单测覆盖。
- **B5**：`HintService` 未改动，提示扣分仍在解锁时独立扣罚，与入账分正交。
- 验证：`mvn test` 13/13 通过；`vite build` 通过。

## 计分模块备忘

- **门禁位置**：Controller（提交入口）与 `ScoringService.recordCorrectSolve` 双重校验；Service 拒绝时抛异常使整个提交事务回滚，不存在「提交标正确但分/一血部分落库」的撕裂。
- **事务边界**：`ContestService.submitAnswer`（`@Transactional`）→ `recordCorrectSolve`（REQUIRED 加入）→ `INSERT IGNORE first_bloods` + `addScore` 原子累加，同一事务提交。
- **并发**：一血由 `unique_first_blood_question` 唯一约束保证同题至多一条、奖金至多一次；总分用原子 `total_score + delta`，无 read-modify-write 丢失更新。
- **旧数据兼容**：`bonus_awarded` 幂等补列、旧行默认 0；`sumBonusAwarded` COALESCE；概览对空库返回全零；配置缺失/非法值一律回退 §8 默认值。
- **B5**：`HintService` 既有扣分逻辑未改动（仍走 `contestUserMapper.update`），与动态入账正交。
- **概览口径选择**：`questions_at_base_points/at_min_points` 按全部 `questions`（含停用题）现场计算；`基础分 < min_points` 的题当前分=min，计入 at_min 而非 at_base。
- 验证：`mvn test` 32/32 通过（ContestServiceTest 7 + ScoringServiceTest 18 + HintServiceTest 2 + ScoringControllerTest 5），jacoco 检查通过；`vite build` 通过。
