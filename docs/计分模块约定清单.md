## ② 一血表名及字段

表名：**`first_bloods`**

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | INT PK AUTO_INCREMENT | 主键 |
| `question_id` | INT NOT NULL | 题目ID；**库级唯一约束** `UNIQUE KEY unique_first_blood_question (question_id)` 保证同题至多一条（§5，不靠应用层 if） |
| `user_id` | INT NOT NULL | 达成一血的用户ID，外键关联 `users(id)` |
| `contest_user_id` | INT NULL | **可选冗余**，便于与 `contest_users` / `submissions` 对齐（§5） |
| `achieved_at` | TIMESTAMP DEFAULT CURRENT_TIMESTAMP | 达成时间 |

**冗余权衡结论（§5 要求写明）**：保留 `contest_user_id` 为可空冗余列。唯一性与计分只依赖 `question_id` + `user_id`；`contest_user_id` 仅用于后轮与 `submissions`（`(contest_user_id, question_id)`）对账，可空以避免历史数据缺失时阻塞写入。

## ③ 基础分最终字段名

**`questions.points`**（沿用现有列，不重命名、不加镜像列）。代码层把 `points` 作为「基础分」语义读取，入账分 = 基础分（P0），集中在 `ScoringService.resolveAccruedPoints(...)`。全程无写死 `+1`（易错对照表首行）。后轮所称「基础分字段」即指 `questions.points`。

## ④ 计分 Service 类名

**`com.ctf.service.ScoringService`**

- 独立于 `ContestService` / `AdminService`（A2）；`ContestService.submitAnswer` 仅在「本次判定正确且此前未答对」时委托它。
- 与之一一对应：`FirstBloodMapper` / `FirstBloodMapper.xml` / `FirstBlood` / `FirstBloodDTO`。
- 入账分累加与一血落库在**同一事务路径**（`submitAnswer` 标注 `@Transactional`，`awardForCorrectSubmission` 亦 `@Transactional`），避免「加了分但一血表无行」的撕裂（§5）。
- 一血判定为**全场维度**（`countByQuestionId`），并发下靠唯一约束 + `DuplicateKeyException` 兜底，不误用「某用户 submissions 是否正确」判断（§7）。

## ⑤ 本模块 API 路径与方法

模块 API 路径前缀（冻结，A4 / §10）：**`/scoring`**（Servlet context-path `/api` → 实际 `/api/scoring`）。

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| GET | `/api/scoring/first-bloods` | 管理端（admin 角色，JWT） | 一血只读列表：题目ID/题目/学号/姓名/达成时间 |

- 安全：不提供「手动指定某人获得一血」的公开接口；一血只由服务端在正确提交时写入（§6）。
- 前端方法：`scoringAPI.getFirstBloods()`。

## ⑥ 是否预置规格书 §8 任一 `scoring.*` 键

**否**，本轮未向 `contest_config` 写入任何 `scoring.*` 默认值。规格书 §8 允许 P0 不写入（键名 P1/P2 启用时启用）；后轮如启用将使用与 §8 完全一致的键字符串（`scoring.min_points` / `scoring.decay_step` / `scoring.first_blood_bonus` / `scoring.freeze_on_end` / `scoring.overview_timezone`），键名不改。比赛时间判断继续复用 `ContestTimeUtil` / `ConfigService`（`startTime`/`endTime`/`readyTime`/`resultsTime`），不平行维护第二套。

## ② 公式里「基础分」对应第一轮哪个字段名

`current_points = max(scoring.min_points, 基础分 − scoring.decay_step × solve_count)` 中的「基础分」= 第一轮冻结的 **`questions.points`**（`ScoringService.resolveAccruedPoints` 读 `question.getPoints()`），未改名、未加镜像列。

## ③ 奖金如何借用第一轮唯一约束满足 B3

一血奖金 `scoring.first_blood_bonus` 仅在 `recordFirstBloodIfAbsent(...)` **成功写入一血的那一次**返回 `true` 时，于同一事务内一并累加到用户总分。去重完全依赖第一轮 `first_bloods` 表的唯一约束 **`unique_first_blood_question (question_id)`**：

- 应用层先 `countByQuestionId` 快速短路；
- 并发下若两笔提交同时判定为一血，第二笔 `insert` 触发 `DuplicateKeyException`，捕获后返回 `false`，**不发放奖金**；
- 因此一题的一血奖金至多发放一次，**未新建任何「奖金发放表」**（B3）。

## ④ B1 的 solve_count 时点：**入账前（before accrual）**

采用**入账前** solve_count（不是入账后）。实现：`submitAnswer` 先把本次正确提交行写入 `submissions`（该表 `(contest_user_id, question_id)` 唯一），随后 `resolveAccruedPoints` 调用 `countCorrectByQuestionExcludingUser(questionId, contestUserId)` —— **排除当前参赛者**统计正确解出人次，得到的正是「本次这一解出计入之前」的 solve_count。

- 第 1 次解出：入账前 solve_count=0 → `max(min, base − step×0)`，仍接近基础分；
- 第 2 次解出：入账前 solve_count=1 → `max(min, base − step×1)`；

与 §15 示例推演一致（base=100/step=10/min=60：100 → 90 → …钳制 60）。已算出的入账分立即写入总分且后续衰减不回算（B2）。B5：提示扣分仍由 `HintService` 负责，不折算进 `decay_step`。

## §8 配置键落地情况（P1）

本轮通过 `PUT /api/scoring/config` 按需 upsert，键字符串与 §8 **完全一致**：`scoring.min_points`、`scoring.decay_step`、`scoring.first_blood_bonus`、`scoring.freeze_on_end`、`scoring.overview_timezone`（后两者 P2 启用，本轮已可存储但计分逻辑暂不消费）。默认值同 §8：`1 / 0 / 0 / true / Asia/Shanghai`。比赛时间判断仍复用 `ContestTimeUtil` / `ConfigService`，未平行维护第二套。

## 最终计分公式与事务边界

- **入账分**（每次正确解出，B1）：`accrued = max(min_points, points − decay_step × solveCountBefore)`；若本次达成一血再 `+ first_blood_bonus`（B3）。
- **solveCountBefore**：`submissions` 中该题除当前参赛者外的正确解出人次（= 入账前）。
- **事务边界**：`ContestService.submitAnswer(@Transactional)` 内，先写/更新 `submissions` 行，再调用 `ScoringService.awardForCorrectSubmission(@Transactional)`（写一血 + 累加总分 + 记 awarded_bonus）。一血与加分要么同成功要么同回滚（§5 无撕裂）。

## 计分模块备忘

### B1 中 solve_count 时点（满足条款 Z9）

**最终实现：`solve_count` 取「入账前」（before accrual）**，引用规格书**条款 B1**。

实现位置 `ScoringService.resolveAccruedPoints`：调用 `submissionMapper.countCorrectByQuestionExcludingUser(questionId, contestUserId)`，统计该题**除当前参赛者外**的正确解出人次。由于 `submitAnswer` 已先把本次正确提交行写入 `submissions`（`(contest_user_id, question_id)` 唯一），"排除当前参赛者"得到的正是"本次这一解出计入之前"的 solve_count。

第 1、2 次解出的计算顺序：
- **第 1 次解出**：入账前 solve_count=0 → `max(min, base − step×0)`，仍等于/接近基础分（若同时首杀再 `+bonus`）。
- **第 2 次解出**：入账前 solve_count=1 → `max(min, base − step×1)`。
- 与规格书 §15 示例一致（base=100/step=10/min=60：100 → 90 → … 触底 60）。已入账分立即写入总分，后续他人解出使 solve_count 增大，**不回算**已入账用户的分（B2）。
